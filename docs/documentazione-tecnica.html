01

Panoramica dell'architettura

Grapes non ha un server proprio: è un client React Native che parla direttamente con un progetto Supabase, che funge da backend completo (database + autenticazione + API + regole di accesso).

L'app è organizzata in tre grandi blocchi:

1. Client (questo repository)

App Expo/React Native in TypeScript. Gira su Android, iOS e Web dallo stesso codice. Contiene schermate, componenti, logica di stato locale e le chiamate al database.

2. Supabase (backend gestito)

Database PostgreSQL reale, autenticazione utenti, API REST auto-generata sulle tabelle, funzioni SQL per le operazioni più delicate. Non c'è un server Node/Express separato da mantenere.

Il client non ha mai accesso diretto e "libero" ai dati: ogni riga di ogni tabella è protetta da una policy di Row Level Security (RLS) a livello di database, che filtra automaticamente i dati in base a chi ha effettuato l'accesso. Questo significa che anche se qualcuno leggesse il codice del client (compreso il file .env con la chiave "anon"), non potrebbe comunque leggere o modificare i dati di un altro utente: il controllo non è "a fiducia" nel client, è imposto dal database stesso.

Le operazioni che toccano più tabelle insieme e devono succedere "tutte o nessuna" (es. spostare scorte tra frigo e freezer, o completare una produzione che consuma ingredienti e crea un semilavorato) non sono scritte come sequenze di chiamate dal client, ma come funzioni PL/pgSQL (RPC) eseguite in un'unica transazione sul database — vedi il capitolo 4.

02

Perché queste tecnologie

Ogni scelta ha un motivo legato ai vincoli del progetto (mantenere React, build nativa Android, sincronizzazione multi-dispositivo) più che a una preferenza generica.

Scelto

React Native + Expo, invece di Kotlin/Java nativo puro

Il brief chiedeva di mantenere React (competenza già presente) e allo stesso tempo ottenere una vera app nativa apribile in Android Studio. Expo aggiunge un livello di produttività sopra React Native: routing a file, hot reload, un ampio set di moduli nativi già pronti (storage, immagini, date picker, calendario, gradient) senza dover scrivere codice Kotlin/Swift a mano per ciascuno.

Alternativa scartata: sviluppo nativo puro (Kotlin) — più lavoro, nessun riuso di React, nessuna portabilità futura su iOS/web.
Scelto

Supabase, invece di Firebase o un backend custom

Il dominio (ingredienti↔scorte↔location, ricette↔varianti↔ingredienti/componenti, ordini↔ricette) è fortemente relazionale, con vincoli e riferimenti incrociati: un database SQL reale con foreign key e check-constraint è più adatto di un database a documenti. Supabase offre Postgres vero, autenticazione pronta, API auto-generata, RLS nativa e funzioni RPC in un unico servizio gestito, ospitabile in regione UE (rilevante per il GDPR, dato che si trattano dati clienti negli ordini).

Alternative scartate: Firebase/Firestore (NoSQL, meno adatto a relazioni complesse) — backend custom Node/Express (server da scrivere, ospitare e mantenere).
Scelto

TanStack Query, invece di Redux

Quasi tutto lo stato dell'app è stato remoto (dati che vivono nel database, non nella memoria del client). TanStack Query gestisce automaticamente cache, invalidazione, nuovi tentativi e stati di caricamento/errore per questo tipo di dati, evitando il boilerplate di Redux (action, reducer, thunk) per quelle che sono, in sostanza, letture e scritture verso il server.

Stato locale (form nelle modali, preferenza di tema, lingua) resta gestito con useState e Context React, dove Redux non aggiungerebbe valore.
Scelto

Expo Router, invece di React Navigation "a mano"

Le schermate corrispondono direttamente ai file dentro src/app. I gruppi (auth) e (app) separano le schermate pubbliche da quelle protette, con Stack.Protected che decide quale gruppo mostrare in base alla sessione. Stesso meccanismo funziona su nativo e web.

Scelto

Funzioni RPC in PostgreSQL per le operazioni transazionali

Spostare scorte, completare una produzione o ricevere un ordine fornitore richiedono di aggiornare più righe/tabelle insieme, senza lasciare lo stato a metà se qualcosa va storto. Farlo con più chiamate separate dal client sarebbe rischioso (rete instabile, chiusura app a metà operazione). Le funzioni move_stock, complete_work_plan_task e receive_purchase_order eseguono tutto in un'unica transazione sul database: o va tutto a buon fine, o nulla viene modificato.

Scelto

Sistema di traduzione custom, invece di i18next

Con solo due lingue e poche centinaia di stringhe statiche, una libreria completa come i18next aggiungerebbe complessità (namespace, plurali, interpolazioni avanzate) non necessaria. Un Context React con due dizionari TypeScript (en.ts / it.ts) che condividono lo stesso "shape" dà anche sicurezza a tempo di compilazione: se manca una chiave in un dizionario, TypeScript lo segnala come errore.

Libreriareact-native-calendars

Per il calendario Ordini: supporta più marcatori colorati nello stesso giorno (uno per ordine), necessario perché più torte possono avere lo stesso ritiro.

Libreriareact-native-gifted-charts

Grafici (linea/barre) pensati per React Native con supporto anche su web tramite react-native-web, evitando di introdurre una libreria solo-browser (es. Chart.js) incompatibile con l'app nativa.

03

Struttura del progetto

Il codice sotto src/ è organizzato per responsabilità, non per tipo di file: ogni funzionalità (ingredienti, ricette, ordini...) ha una propria cartella con dati, logica e modali insieme.

src/ ├── app/ ← una route per file (Expo Router) │ ├── (auth)/ login e registrazione, pubbliche │ └── (app)/ tutte le schermate protette da login ├── components/ ← componenti UI generici, riusabili ovunque │ ├── ui/ Card, Button, Modal, Select, Badge... │ └── layout/ Sidebar, BottomTabBar, AppShell, PageHeader ├── features/ ← un modulo per dominio applicativo │ ├── auth/ ingredients/ recipes/ components/ │ ├── orders/ work-plan/ purchase-orders/ │ ├── cost-analysis/ settings/ │ └── ogni modulo: api.ts (query Supabase) + hooks.ts (React Query) + modali ├── lib/ ← client Supabase, query client, helper stock ├── i18n/ ← dizionari EN/IT + provider ├── constants/ ← tema colori, navigazione, unità di misura ├── types/ ← tipi TypeScript che rispecchiano le tabelle DB └── hooks/ ← useTheme, useColorScheme supabase/ ├── schema.sql ← schema completo, per un progetto nuovo └── migration-*.sql ← modifiche incrementali per un progetto già live

Questa organizzazione "per feature" (invece che "per tipo", es. tutti gli hook in una cartella, tutti i componenti in un'altra) mantiene vicino tutto ciò che riguarda una stessa funzionalità: se devi capire come funzionano gli ordini, tutto quello che ti serve è in src/features/orders/ e nella schermata src/app/(app)/orders.tsx.

04

Il modello dati (Supabase)

Tutte le tabelle vivono nello schema public, hanno Row Level Security attiva e sono filtrate per owner_id (l'utente proprietario) — direttamente o tramite le tabelle "genitore".

Tabelle principali

TabellaA cosa serve
profilesUn profilo per utente (nome pasticceria, lingua preferita). Creato automaticamente alla registrazione.
storage_locationsLe location di stoccaggio (Frigo/Freezer/Dispensa), 3 create in automatico per ogni nuovo utente.
ingredients / ingredient_stockIngredienti grezzi e relativa quantità per location, con soglia minima per gli alert.
stock_movementsStorico degli spostamenti di scorte tra location.
components / component_ingredients / component_stockSemilavorati/preparazioni riutilizzabili (es. frolla): la loro "ricetta" di ingredienti grezzi, il costo/unità calcolato, e lo stock del prodotto una volta preparato.
recipes / recipe_variants / recipe_variant_ingredientsRicette finite, con una o più varianti (dosi diverse, es. torta da 500g/1kg/2kg), ciascuna con la propria lista di ingredienti e/o componenti.
recipe_variant_stockStock di prodotto finito per variante (es. torte già pronte), per location.
ordersOrdini clienti: nome torta libero, ricetta collegata opzionale, data ritiro, stato, prezzo.
work_plan_tasksTask del piano di lavoro, giorno per giorno; opzionalmente collegati alla produzione di un componente o di una variante.
purchase_orders / purchase_order_itemsOrdini di materie prime ai fornitori, con le righe articolo (ingrediente, quantità, location, costo).
cost_historyStorico dei cambi di costo/unità degli ingredienti, popolato automaticamente da un trigger.

Le tre funzioni RPC

Ogni funzione gira in una singola transazione: se un controllo fallisce a metà (es. scorte insufficienti), raise exception annulla tutto quello fatto fino a quel punto.

FunzioneCosa fa
move_stock(ingrediente, da, a, quantità)Scala la quantità dalla location di origine, la aggiunge a quella di destinazione, registra il movimento. Usata dal modale "Sposta scorte" negli Ingredienti.
complete_work_plan_task(task, location_origine)Legge la ricetta/composizione del componente o variante collegati al task, scala dagli ingredienti/componenti grezzi (nella location indicata) la quantità necessaria in proporzione a quanto va prodotto, poi aggiunge il prodotto finito allo stock nella location target del task, e segna il task completato.
receive_purchase_order(ordine)Per ogni riga dell'ordine fornitore, aggiunge la quantità allo stock ingredienti nella location indicata; se è stato specificato un costo/unità, aggiorna anche il costo dell'ingrediente (che a cascata alimenta lo storico costi).

Due trigger automatici

handle_new_user — alla creazione di un account (evento auth.users), crea il profilo e le 3 location di default.
log_ingredient_cost_change — ogni volta che cost_per_unit di un ingrediente cambia (creazione o modifica), inserisce automaticamente una riga in cost_history, così i grafici di Analisi Costi hanno sempre dati reali senza bisogno di una scrittura esplicita dal client.

Nota sui componenti come "ingrediente". La tabella recipe_variant_ingredients ha sia ingredient_id che component_id, ma un vincolo check impone che sia valorizzato uno solo dei due per riga. Questo permette a una ricetta di essere composta sia da ingredienti grezzi diretti sia da semilavorati con il proprio costo già calcolato (es. Torta al limone = Frolla + Lemon curd + Glassa, ciascuno con dose e costo/kg propri).
05

Design system e componenti condivisi

Un'unica fonte di verità per i colori (src/constants/theme.ts) alimenta ogni schermo, sia in tema chiaro che scuro.

I colori non sono mai scritti "a mano" (es. #7C3AED) dentro le schermate: ogni componente legge i valori tramite l'hook useTheme(), che restituisce la palette corretta in base alla preferenza dell'utente (Automatico/Chiaro/Scuro, gestita da ThemePreferenceProvider e salvata localmente). Cambiare l'aspetto dell'intera app significa quindi modificare un solo file.

TokenUso
background / surfaceSfondo pagina (crema) e sfondo delle card (bianco)
primary / accentViola: bottoni pieni e testo/badge d'accento
sidebar / sidebarActiveBgSidebar e stato della voce di menu attiva
danger / warning / success / info (+ varianti *Bg)Stati semantici: alert scorte basse, badge ordine, variazioni di costo

Sopra il tema, src/components/ui/ raccoglie i "mattoncini" riusati in tutte le schermate: Card, Badge, Button, TextField, Select, Modal (finestra di dialogo centrata), DateField (selettore data nativo), SearchInput, SegmentedTabs, StatCard, EmptyState, IconButton. Nessuna schermata definisce il proprio bottone o la propria card da zero.

06

Autenticazione, sessione e sicurezza

src/features/auth/AuthProvider.tsx avvolge tutta l'app e mette a disposizione sessione utente, login, registrazione e logout.

Il flusso è interamente delegato a Supabase Auth (email + password). Alla registrazione, il trigger handle_new_user crea profilo e location di default lato database, non lato client — così anche registrandosi da un dispositivo diverso in futuro, il comportamento resta identico.

Il router (src/app/_layout.tsx) usa Stack.Protected: se c'è una sessione valida mostra il gruppo (app), altrimenti (auth). Non serve controllare manualmente la sessione in ogni schermata.

Un dettaglio tecnico non ovvio: su web, Expo Router pre-renderizza le pagine anche lato server (Node), dove l'oggetto window non esiste. Il client Supabase di default usa AsyncStorage, la cui implementazione web tenta di accedere a window.localStorage — mandando in crash il rendering server-side. src/lib/supabase.ts risolve il problema con uno storage adapter che, su web, legge/scrive localStorage solo se window esiste, altrimenti è un no-op.

Ogni tabella ha RLS attiva con policy owner_id = auth.uid() (diretta o tramite join alla tabella genitore). Anche se un bug nel client tentasse di leggere o scrivere dati di un altro utente, il database rifiuterebbe la richiesta: la sicurezza non dipende dalla correttezza del codice React.

07

Lingua e tema

Due Context React indipendenti, entrambi montati nel layout radice.

Lingua (src/i18n/)

en.ts e it.ts esportano un oggetto identico nella forma (TypeScript obbliga entrambi ad avere le stesse chiavi). I18nProvider rileva la lingua del dispositivo al primo avvio (expo-localization), poi ProfileLanguageSync allinea la lingua a quella salvata sul profilo Supabase appena disponibile — così la preferenza segue l'utente su qualsiasi dispositivo acceda.

Tema (src/features/settings/ThemePreferenceProvider.tsx)

Tre stati: Automatico (segue il sistema operativo tramite useColorScheme()), Chiaro, Scuro. La scelta è salvata in AsyncStorage — locale al dispositivo, non sincronizzata (a differenza della lingua, è considerata una preferenza di visualizzazione più che un dato utente).

08

Le funzionalità, modulo per modulo

Per ogni modulo: a cosa serve, quali file lo compongono, e la logica non ovvia.

Dashboard

Fileapp/(app)/index.tsx

Non ha una propria cartella in features/: legge dati già esposti da useIngredients, useRecipes e useStorageLocations e li aggrega con useMemo (conteggio scorte per location, alert sotto soglia, margine medio, top ricette per margine).

Ingredienti

Filefeatures/ingredients/ + app/(app)/ingredients.tsx

fetchIngredients() unisce la tabella ingredients con ingredient_stock e restituisce, per ciascun ingrediente, un oggetto stock indicizzato per tipo di location ({'{'} fridge, freezer, pantry {'}'}) — comodo per tabelle e filtri. Il modale "Sposta scorte" chiama la RPC move_stock invece di fare due update separati.

Ricette & Componenti

Filefeatures/recipes/, features/components/ + app/(app)/recipes.tsx (due tab nella stessa schermata)

Il costo di un componente è sempre calcolato, mai inserito a mano: costPerUnit = costo totale ingredienti ÷ resa del batch. Il costo di una variante di ricetta somma il costo di ogni riga: se la riga referenzia un ingrediente, quantità × costo_unità_ingrediente; se referenzia un componente, quantità × costPerUnit_componente (già calcolato al punto sopra). Margine e percentuale margine si ricavano di conseguenza da prezzo_vendita − costo.

Piano di lavoro

Filefeatures/work-plan/ + app/(app)/work-plan.tsx

Vista giorno per giorno (navigazione con frecce). Un task può essere libero (semplice checklist) o di produzione (collegato a un componente o a una variante, con quantità e location di destinazione). Completare un task libero aggiorna subito lo stato; completare un task di produzione apre CompleteTaskModal, che chiede da quale location prelevare gli ingredienti/componenti, poi chiama la RPC complete_work_plan_task descritta al capitolo 4.

Ordini

Filefeatures/orders/ + app/(app)/orders.tsx

Il nome della torta (cake_name) è testo libero e obbligatorio; la ricetta collegata è facoltativa e serve solo a chi vuole tracciare il costo dell'ordine — non influenza il prezzo, che resta sempre inserito manualmente. Il calendario (react-native-calendars) mostra un pallino colorato per stato ordine su ogni giorno con prenotazioni.

Acquisti

Filefeatures/purchase-orders/ + app/(app)/purchases.tsx

Un ordine fornitore ha più righe (ingrediente, quantità, location, costo/unità opzionale). "Segna come arrivato" chiama receive_purchase_order: aggiorna le scorte e, se presente il costo, anche il prezzo dell'ingrediente — azione irreversibile via UI (coerente con un arrivo merce reale).

Analisi costi

Filefeatures/cost-analysis/ + app/(app)/cost-analysis.tsx

Legge cost_history (popolata dal trigger, capitolo 4) e aggrega lato client: media mensile per l'andamento nell'anno selezionato (con "carry-forward" dei mesi senza variazioni), media annua per il confronto anno su anno.

In esaurimento

Fileapp/(app)/low-stock.tsx

Raggruppa per location tutti gli ingredienti con quantity ≤ min_threshold (soglia impostata per location nel modale ingrediente) — la stessa logica usata per il riquadro "Low stock alerts" della Dashboard, ma completa e navigabile.

09

Navigazione e layout responsivo

AppShell sceglie il layout in base alla larghezza dello schermo (soglia 820px, TabletBreakpoint in theme.ts), non in base al sistema operativo — così un Android in modalità tablet o con finestra ridimensionata si comporta correttamente.

Tablet / Desktop / Web largo

Sidebar fissa a sinistra con tutte le 8 sezioni, più Impostazioni e Esci in fondo.

Telefono

BottomTabBar con le 4 sezioni più usate (Dashboard, Piano di lavoro, Ricette, Ordini) + "Altro", che elenca le rimanenti (Ingredienti, In esaurimento, Acquisti, Analisi costi).

Entrambe le navigazioni leggono lo stesso array sidebarNavItems/mobileTabItems in src/constants/navigation.ts: aggiungere una nuova sezione all'app richiede di aggiungerla lì una sola volta.
